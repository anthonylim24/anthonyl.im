# Observability and self-healing

| Piece | Location | Notes |
|-------|----------|-------|
| Request ids, access log, counters | `server/src/observability.ts` (`requestLog`, `onError`) | Every response carries `X-Request-Id` (Cloudflare's ray id when present). One log line per request (`GET /api/trips 200 12ms id=…`); quiet for assets and `/health`. Thrown errors go through `app.onError` and answer JSON with the `requestId` |
| `/health` | `server/app.ts` | Answers from memory. Deploys, the uptime workflow and the droplet watchdog poll it; keep it dependency-free |
| `/health/ready` | `createReadiness` | Asks Clerk's Frontend API, Supabase and the built frontend, each with a 4 s deadline, cached 20 s. 503 with per-check detail when one is down |
| `/health/metrics` | `metricsSnapshot`, `canReadMetrics` | Request counts, 4xx / 5xx, p50 / p95 per group (api, clerk, asset, page), memory, named counters (`clerk_proxy.failures`, `client.<kind>`). In memory; a restart resets it. Not public: 403 unless the request is local (`curl localhost:3000/health/metrics` on the droplet: a loopback peer with no `CF-Connecting-IP` / `X-Forwarded-For` / `X-Real-IP`) or sends `Authorization: Bearer $METRICS_TOKEN`. Nothing automated reads it. nginx sets `X-Forwarded-For` / `X-Real-IP` on every proxied request (`deploy/nginx/anthonyl.im.conf`, applied by hand with `deploy/install-droplet.sh`), so nothing that came through nginx looks local |
| Security headers | `server/src/securityHeaders.ts` | Every response: HSTS (one year, no `includeSubDomains`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (PR previews keep `no-referrer`), and a CSP of only `frame-ancestors 'self'`. A fuller CSP would have to list Clerk, the map tiles, Google 3D Tiles and PostHog |
| Rate limits | `server/src/middleware/rateLimit.ts` | In memory, at most 10,000 buckets (oldest evicted), expired ones swept every 30 s. Keyed on `CF-Connecting-IP`, else the last `X-Forwarded-For` hop (never the first: the caller writes it). Signed-in routes (trips, Instagram enqueue) key on the Clerk user. 429 with `Retry-After` |
| Browser error beacon | `POST /api/telemetry`, `frontend/src/lib/telemetry.ts` | `reportClientEvent(kind, message, detail)` writes a `[client] …` line to the server log: uncaught errors, unhandled rejections, route crashes, missing chunks, stalled sign-in. Deduplicated, ten a page, never throws. It goes to our own origin because networks that break the page usually block third-party analytics too |
| Clerk proxy | `server/src/clerkProxy.ts` | 10 s deadline per attempt; a read is retried once on a network error or 502–504, a write never; a dead upstream answers 502 in Clerk's error shape. Cookies scoped to another domain (Clerk's Cloudflare sets `__cf_bm` / `_cfuvid` for its own) are dropped, since a browser here rejects them and Cloudflare will not cache a response that sets one; that is what lets the edge cache version-pinned `/__clerk/npm/@clerk/clerk-js@x.y.z/…` files |
| Stalled sign-in | `frontend/src/lib/authStall.ts`, `TripsLayout` | If Clerk has not loaded after 10 s (or reports `error`), `diagnose` probes `/health` and the proxy, the gate says what is unreachable (offline; the network, when `/health` gets no answer at all; this site, when it answers 5xx; sign-in), keeps probing with backoff, and reloads (at most twice a tab) once everything answers |

Outside the app: a systemd watchdog on the droplet restarts PM2 after three failed `/health` checks, nginx serves a self-reloading outage page for 502 / 503 / 504, and `.github/workflows/uptime.yml` probes production every 15 minutes and opens an `uptime` issue on failure. Files and install steps: [`deploy/README.md`](../deploy/README.md).

Some home networks (Xfinity Advanced Security) block `anthonyl.im` hostnames over TCP while HTTP/3 still gets through, so a visitor can see the shell load and sign-in fail. That is the case the stalled sign-in screen exists for, and why a request with no answer is blamed on the network rather than the site: Cloudflare answers for this site even when the droplet is down. It cannot be fixed from the server.
